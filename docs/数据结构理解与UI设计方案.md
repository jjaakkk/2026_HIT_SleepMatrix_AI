- **项目来源**：与中科院材料所、国内某上市公司合作研发的智能床垫产品。

### 系统架构（第 5 页图，视觉模型核验）
三层闭环架构：**感知层**（床垫传感器 + 嵌入式处理器采集上传）→ **平台层**（云端服务器：睡姿识别 + 气垫调节算法）→ **应用层**（手机 App + 大屏可视化系统：睡眠质量报告、床垫受压数据、手动与自适应调节闭环）。
→ 本项目落点：**应用层的"大屏可视化系统"**，是整条产品链路中直接面向人机交互的出口；睡姿识别（算法组）与气垫调节（平台层）的输出将来可接入我们的数据接口。

### 1. 一帧数据是什么（已实测）

**一帧 = 44 行 × 24 列 = 1056 个压力传感器值。**（新版 44×24 已核实；旧版为 40×26=1040，二者不可混用。）

- **行（y，0–43）＝人体纵轴（头→脚）**：行 0 是头端，行 43 是脚端。实测依据：仰卧帧中行 0–2 几乎全零（头部轻触/无接触），压力峰值集中在行 18–27（与"臀部"区域标注一致），行 36–44 为小腿区。
- **列（x，0–23）＝人体横轴（左右）**：列 12 为中线（脊柱点全部在列 12）。
- **txt 文件结构**：每行 24 个逗号分隔值 = 矩阵的一行；**连续 44 行 = 一帧；帧与帧之间以 1 行空行分隔**（飞书文档所述，已实测：wzh_10.txt 共 1349 行 = 30 帧 × 45 行 − 末帧无尾空行；空行位于行 44、89、134…）。动态文件中间隔行不是空行而是 0/1/2 睡姿标签行（官方说明：**标签行忽视即可**）。例：`wzh_10.txt` 1320 个数据行 = 30 帧。
- **data.json 结构**：`data` 字段为逗号分隔字符串，1056 个值，**行优先排列**（前 24 个 = 第 0 行）。
- **原始值范围**：实测 0 ~ 841（841 为全库最大帧峰值；典型仰卧帧峰值 148~460，中位数约 310；侧卧峰值更高，SAI 侧卧 frame0 达 488）。
- **是否存在 0 值**：大量存在。床垫边缘恒为零，身体轮廓外为零，人身上也有零值（抽样零值占比约 16%）。
- **空载/背景压力**：✅ 存在。每人有 `xxx_空载.txt`（15 帧）。实测 SAI 空载均值帧：均值 4.29、单点最大 27、个别帧单点可达 42。**背景不是 0**，计算接触面积等指标前应扣除空载均值帧。
- **是否需要归一化/插值/平滑**：
  - 归一化：显示用，建议按帧自适应（0→透明/深色，帧最大→亮色），并给固定档位（如 0-300 / 0-500 / 自动）。
  - 插值：**建议做**（见第六部分热力图设计），原始 44×24 直接放大是马赛克，双线性/双三次插值后才能形成连续人体轮廓。
  - 平滑：可选。逐帧指标曲线建议做 3~5 点滑动平均（帧间存在抖动）；热力图本身不建议过度平滑（避免失真）。

**⚠️ 重大发现——每个键有 2 份副本（= 数据增强镜像，已实测 1056/1056 证实）：** `(people, action, frame)` 组合出现 2 次，副本 B = 副本 A 的**左右镜像**（列 c → 23−c）。飞书数据集说明确认了增强规则：

- 区域划分数据集同样用镜像扩为 2 倍（14400 = 20 人 × 21 动作 × 15/30 帧 × 2）；
- 官方特别提醒：**训练时不要重复使用对称进行数据增强**（对我们可视化无影响，但回放必须区分镜像帧）。
- 镜像帧的 `region` 是**重新人工标注**的（副本 B region 与副本 A 的镜像坐标不一致、略有人工偏差），不是坐标镜像——但两份标注都直接可用。
- json 内记录顺序是 A、B 交替（0,0,1,1,2,2…），**不是时间顺序**。
- **播放策略（重要修正）**：真正的连续时间序列只有原始帧（15/30 帧）；**默认只回放副本 A（原始帧）**；提供"含镜像增强帧"开关（播完原始帧再播镜像帧，界面角标"镜像增强帧"）。若读 txt，同理：默认只取前半段（仰卧/俯卧）或只取本动作原始段（侧卧前半段）；数据与 json 逐值相等可直接匹配标注。

**txt 文件名含义**：`人名_N.txt` = 该人 action N；`人名_空载.txt` = 背景；`人名_动态一/二.txt` = 睡姿连续变化过程（见下）。

**动态文件（回放 Demo 的金矿）**：`whz_动态一.txt` 共 159 帧，每帧 = 44 行数据 + 1 行睡姿标记（0/1/2/3）。实测 wzh 的标记序列：`0×11 → 2×10 → 0×14 → 2×10 → 0×10 → 1×14 → 0×9 → 1×11 → 0×14 → 2×10 → 0×10 → 2×12 → 0×12 → 1×11`，即**仰卧⇄左侧卧⇄俯卧的连续翻身过程**，且每帧都带真实睡姿标签——可直接用于"实时睡姿检测"演示。有动态文件的人：dgs、gzy、jhy、ltr、lyp、sbr、syz、tjs、wcy、whc、wjy、wzh、yl、zhr（14 人）。

### 4. region（已实测并解析）

**编码规则**（由 docx 表 + 旧版 json 模板 + 解剖学验证三方确认）：
`region = "x1 x2 … x12 y1 y2 … y12"` —— **前 12 个数是所有区域角的 x（列）坐标，后 12 个是 y（行）坐标**（与 spine 同一种"先 x 块后 y 块"约定，旧版数据同为该约定）。

第 i 个部位（i=1…6）：左上角 `(x[2i-1], y[2i-1])`，右下角 `(x[2i], y[2i])`，顺序固定为：**肩部、背部、腰部、臀部、大腿部、小腿部**。

实测 SAI 仰卧（action1）示例解析：

| 部位 | 列范围 x | 行范围 y |
|---|---|---|
| 肩部 | 6–18 | 3–8 |
| 背部 | 6–18 | 8–13 |
| 腰部 | 6–18 | 13–18 |
| 臀部 | 5–20 | 18–27 |
| 大腿部 | 5–20 | 27–36 |
| 小腿部 | 6–20 | 36–44* |

（*右下角行 y=44 超出矩阵行号 0–43，全库共 1350 处、x=24 共 989 处——按"开区间/右边界排他"理解即可，即实际覆盖到行 43；渲染时对 x2、y2 做 clamp 到 [0,23]/[0,43]。）

**⚠️ 与任务描述冲突**：任务说"区域数据对应肩背腰臀大腿小腿六个区域"——**只有 SAI、dgs、gzy 3 人有完整 6 区域标注（含小腿）；其余 17 人小腿部 4 个坐标均为 `na`（全库 12240 条、位置一致），且这 17 人 `spine` 全为 `na`**。飞书文档明确：**"小腿部只标注前 3 人，其他为 na，不使用，仅需划分其他 5 区域，不考虑小腿部"；spine"仅标记 3 人，其余为 na，暂不使用"**。设计上：默认只展示**肩/背/腰/臀/大腿 5 区域**；小腿部与脊柱仅对 SAI/dgs/gzy 三人可选显示（真实标注，展示无妨，算法不用）。有数据才画，无数据显示"该用户无此标注"。

（注：飞书文档中 region 顺序表述为"x1,x2,...,x6,y1,y2,...,y6"，与实际数据不符——实际 region 字符串为 24 个 token = [12 个 x][12 个 y]，按实际文件解析为准，已通过解剖学验证。）

**region 用于可视化**：
- 热力图上叠加彩色半透明区域框/色带（六段身体区域沿纵向排列）；
- 区域标签（肩/背/腰/臀/大腿/小腿）；
- 逐区域统计（均值/峰值/接触点数），区域压力排行卡片——"现在哪个部位受力最大"一目了然；
- 悬浮/点击区域 → 高亮 + 该区域指标详情。

### 5. spine（已实测并解析）

`spine = "x1 x2 x3 x4 x5 y1 y2 y3 y4 y5"`（docx 原文定义），5 个点 `(x_i, y_i)`。实测 SAI 仰卧：5 点 = (12,3) (12,6) (12,11) (12,15) (12,19) —— **全部在列 12（人体中线）上，从胸部到臀部自上而下 5 个点**。俯卧/侧卧时 x 会随身体倾斜（如俯卧 x=10,10,11,11,11）。仅 SAI/dgs/gzy 三人有。
**适合**在热力图上画成"脊柱辅助线"（5 点连线 + 节点圆点），答辩时直观展示身体中轴线与受力关系。

## 第五部分：核心可视化设计

### 1. 压力热力图（视觉核心）

**问题：直接 44×24 还是插值放大？——建议：插值放大为主 + 原始网格切换。**
理由：① 44×24 只有 1056 点，直接显示是大颗粒马赛克，无法形成"连续人体轮廓"（任务要求）；② 参考图（origin_heatmap 系列）本身就是插值/平滑后的连续热力图；③ 答辩需要"看起来像人体"的效果；④ 但数据真实性同样重要——提供"原始网格"开关（关插值、按 44×24 格子着色 + 数值悬浮），一键证明"每个像素都来自真实传感器"。

- 渲染管线：`1056 原始值 → 空载扣除(可选) → 非线性压扩(p^0.6) → 双线性插值到 ~704×384 显示网格 → Canvas 逐像素着色`。每帧重算开销约 10 万像素级，60fps 无压力。
- 颜色映射：**turbo 色带**（飞书官方推荐 `cmap="turbo"`：深蓝=低 → 青 → 绿 → 黄 → 橙 → 红=高，"红色为高压力区域，蓝绿色表示低压力区域"）；低压力透明→深蓝，床垫外区域全透明（深色底）。JS 端实现 turbo 官方 256 阶 LUT。参考图实测规范：固定色标 0–250，刻度 0/50/100/150/200/250。
- 插值：官方示例同样用 `interpolation='bilinear'`（双线性）——与我们的插值方案一致；原始网格模式对应官方 `ax.grid(alpha=0.3)` 细网格效果。
- 数值范围：三档——`固定 0–250（与参考图一致，默认）`、`自动（按当前帧最大值）`、`固定 0–500`。侧卧峰值 488、仰卧峰值 ~286，默认档直接对齐项目组参考图风格。
- 显示模式（三种，可切换）：**标准**（p^0.6 压扩）、**弱力增强**（p^0.35 更强压扩，放大躯干弱压力区域，呼应弱力组课题与课程"躯干显示更明显"要求，角标明示为显示增强）、**原始网格**（44×24 格子直显 + 数值悬浮，证明数据真实）。
- 坐标方向：**头在上、脚在下**（行 0 在画布顶端），与参考热力图、区域条带、脊柱线一致；画布四周画 44×24 刻度；画面角落显示数据来源标签（如"SAI_1.txt 第41帧"，参考图同款）。
- 叠加层：区域半透明色带 + 区域边框（参考图即用浅红/粉描边矩形框 + 灰色虚线人体外边界框 + 红色关键参考点，本设计沿用并升级为六部位语义色）+ 脊柱 5 点连线（可开关）；悬浮任意像素 → tooltip 显示 `(行,列)=压力值`。
- 动画：帧间切换 60fps；在"原始网格"模式下支持 8×8 分块淡入过渡，避免闪跳。

### 2. 人体区域可视化

- 六段色带沿纵向叠加（每段一种半透明主题色 + 顶部标签"肩/背/腰/臀/大腿/小腿"），色带透明度不遮压力色。
- 区域统计卡（右栏）：每区域 均值压力、峰值、接触点数，**按当前帧峰值排序 + 条形条**——评委一眼看到"现在臀部受力最大"。
- 悬浮/点击区域 → 该区域高亮描边 + 右栏锁定显示其指标；点击曲线图切换为"该区域压力曲线"。
- 侧卧时区域框会随 `region` 数据整体偏移（数据自带，非我们推算）——这就是"不同睡姿下区域变化"的真实来源。
- 无标注（17 人缺小腿 / 无脊柱）→ 不画并显示"当前用户无该标注"小徽标。

### 3. 实时压力指标（全部可从现有数据计算）

| 指标 | 数据来源 | 计算方式（建议） | 单位 | 刷新 |
|---|---|---|---|---|
| 最大压力 | 当前帧 1056 值 | 扣背景后最大值（同时显示原始值） | 传感器读数 | 每帧 |
| 平均压力 | 当前帧 | 有效接触点（扣背景后>阈值，建议阈值 20）的均值 | 传感器读数 | 每帧 |
| 接触面积/有效点数 | 当前帧 + 该人空载帧 | 有效接触点个数，占比 = 个数/1056 | 点 / % | 每帧 |
| 接触面指数（⚠️无官方定义） | 同上 | **候选定义：接触面指数 = (有效接触点数/1056)×100 × 加权(峰值/300)**；或简化为接触面积占比。需项目组确认后定稿 | 指数 | 每帧 |
| 区域均值/峰值 | region + 当前帧 | 区域内扣背景后的均值/峰值 | 传感器读数 | 每帧 |

阈值 20 的由来：实测空载单点最大 42、均值 4.3，取 20 可滤除绝大部分背景（此为本设计建议值，可调）。

### 4. 压力随时间变化

- 曲线：总最大压力、总平均压力、接触面积占比、选定区域压力（默认臀部+腰部两条）。
- 与回放强绑定：播放头跟随帧游标；拖动进度条 → 热力图与指标卡同步跳帧；倍速 0.5/1/2/4×（>1 倍用 `requestAnimationFrame` 每 tick 跳多帧）。
- 曲线窗口：近 200 帧滚动窗口 + 全程缩略图（mini map）。
- 动态文件回放时：曲线区顶部叠加"睡姿事件条"（不同底色 = 不同睡姿，标签在切换点弹出"仰卧→左侧卧"）——把"实时检测睡眠状态"做得非常直观。

### 5. 气囊可视化（课程必选要求；无真实数据 → 模拟 + 预留，绝不造假）

- 课程要求"展示气囊调节对人体的支撑效果"与"实时展示气囊状态变化过程"是**必选**，但数据集与图纸均无气囊状态读数——因此本模块 = **条带布局示意（真实图纸布局）+ 状态模拟器 + 明确标注**：
- 底部条带示意：按布置图编号体系——**左右半区各一组**：左半区上段气囊带 40/41/42（绿）+ 下段 12（红），右半区上段 64/65/66（橙黄）+ 下段 13（红）；条带与热力图六部位纵向对齐（上段≈肩/背/腰，下段≈臀/大腿），条带长度按床垫 1800×2000mm 比例。悬浮条带显示对应传感器编号（0–67 体系）。
- 支撑效果联动演示（模拟剧本）：播放"腰部支撑增强"模拟 → 腰部气囊条变色/变高 → 同步观察热力图腰部区域压力带变化（压力数据仍是真实回放，仅气囊状态是模拟）——视觉上呈现"气囊调节 → 支撑变化 → 压力分布变化"的因果链，但角标始终显示"模拟数据"。
- 预留接口：`AirbagState {zoneId, pressure, timestamp}`，未来设备/后端就绪后替换模拟器即可，UI 不变。

### 6. 数据回放模式

- 数据源面板：`用户 [SAI ▼] ｜ 类型 [静态动作 / 动态过程 ▼] ｜ 动作 [Action 1 ▼] ｜ 睡姿 [自动跟随数据]`。
- 帧号 `125/300` + 进度条 + `⏮ ◀ ▶/Ⅱ ⏭` + 倍速。

## 第六部分：技术选型（对比与推荐）

### 方案 A：Web / JS（推荐 ✅）

- 技术栈建议：**Vite + Vue 3 + TypeScript + Canvas 2D（热力图自绘）+ ECharts（指标曲线）+ 可选 Pinia**；无需后端，数据文件直接放 `public/data/`（大文件可用 fetch 流式加载或预索引）。
- 优点：数据天然是 JSON/TXT，浏览器零转换；Canvas 逐像素控制热力图质量与性能；ECharts 现成解决曲线/交互；`npm run build` 后一个文件夹即可在任何答辩电脑上打开（或 `npx serve`）；WebSocket 是浏览器原生能力，未来接设备**零成本**；开发周期短（1–2 周可出完整 Demo）；团队成员若熟悉前端则维护成本极低。
- 缺点：热力图极致性能不如 GPU 方案（但本项目 1056 点规模 Canvas 绰绰有余）；需要一台装有浏览器的电脑（答辩环境基本必有）。

### 方案 B：Unity

- 实现路径：Unity UI + `Texture2D`/Shader 做 2D 热力图，C# 解析 JSON/TXT，Windows 构建。
- 优点：视觉上限高（shader 级效果）；作为"嵌入式/硬件课程"观感更强。
- 缺点：**开发成本明显更高**——C# 解析 76MB JSON、UI 布局、曲线图全部要从头造轮子（无 ECharts 等价物）；构建产物体积大、每次改 UI 需重新构建；答辩现场需要 .exe 运行环境与屏幕适配；团队若无人精通 Unity，风险集中在个别成员；对"数据回放系统"这种 CRUD+图表型应用，Unity 是杀鸡用牛刀。

**结论：推荐方案 A（Web/JS）**。理由：本项目本质是"数据可视化 + 回放控制"，Web 生态在该领域的成熟度（Canvas + ECharts + WebSocket）直接决定开发成本只有 Unity 的 1/3~1/2，且课程要求明确允许"使用 Unity 或 JS 实现"；Unity 保留为"若团队已有成熟 Unity 开发者且追求展示效果"的备选。**最终建议：Vue3 + Canvas + ECharts 单页应用。**

### 3. 交互逻辑
- 选用户/动作 → 解析器预加载帧 → 自动跳到帧 0 暂停；换源时曲线清空。
- 播放 → 每帧事件广播（帧号+数据）→ 热力图/指标/曲线三处同步刷新。
- 点击热力图区域 → 锁定该区域，E1 切换为该区域曲线；再点空白解除。
- 悬浮热力图任意点 → tooltip `(行x, 列y) = 值`；原始网格模式下逐格高亮。
- 拖进度条 → 直接 seek 对应帧（曲线播放头与热力图同步跳变）。

function parseFrame(raw) {            // raw: 1056 个数的数组
  const rows = 44, cols = 24;
  // matrix[row][col]，row 0 = 头，col 12 = 中线
  return raw.map(Number);
}
// region: "x1..x12 y1..y12" → 6 区域 {x1,y1,x2,y2}，坐标 = (列,行)
function parseRegion(str) {
  const t = str.split(' ').map(s => s === 'na' ? null : +s);
  const xs = t.slice(0, 12), ys = t.slice(12);
  return [0,1,2,3,4,5].map(i => ({ x1: xs[2*i], y1: ys[2*i],
                                   x2: clamp(xs[2*i+1],23), y2: clamp(ys[2*i+1],43) }));
}
// spine: "x1..x5 y1..y5" → 5 点 (列,行)
function parseSpine(str) {
  const t = str.split(' ').map(Number);
  return t.slice(0,5).map((x, i) => ({ x, y: t[5+i] }));
}
